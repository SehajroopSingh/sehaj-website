Here's what each rung taught me, the enemy AI I built for the team game, and the game itself.

Team project

The game

For the final project our team designed and built a complete game in Unity: a start menu, a playable level with characters, physics and AI-driven opponents, and an ending. Everything in it traces back to one of the four milestones below.

What I built: the enemy AI

Every enemy in the game runs on a finite state machine I wrote from scratch in C#. Each enemy is always in exactly one state, each state owns one behavior, and the transitions between them are the rules that make an enemy feel like it is paying attention. I coded the machine itself, every state and action in it, the senses that feed it, and the hooks that drive the enemy's animation.

The machine

A MonoBehaviour that holds the current state, calls that state's update every frame, and switches states through one ChangeState method that runs the old state's exit code and the new state's enter code. That one method is where every transition goes, so there is exactly one place to log, debug or add a rule.

Under the hood

Each state is its own class with Enter, Tick and Exit. Enter sets up what the state needs (a destination, an animator flag, a timer); Tick runs the behavior and checks the transition rules in priority order; Exit clears what Enter set up. Keeping the rules inside each state, rather than in one big switch, meant a new behavior was a new file, not a bigger file. The enemy's shared data (its NavMeshAgent, animator, health, the player reference, tuning values) lives on the controller, and states reach it through a reference passed in at construction.

class EnemyController : MonoBehaviour
    EnemyState current
    void Update()        { senses.Tick(); current.Tick(); }
    void ChangeState(next) { current.Exit(); current = next; current.Enter(); }

class ChaseState : EnemyState
    Enter: agent.speed = runSpeed; anim.SetBool("running", true)
    Tick:  if (health.low)            → ChangeState(retreat)
           if (senses.inAttackRange) → ChangeState(attack)
           if (!senses.canSeePlayer && lostFor > giveUpTime) → ChangeState(search)
           agent.SetDestination(player.position)   # re-pathed on a short timer

Senses

Before any state runs, a small perception component works out what the enemy knows: can it see the player, can it hear them, how far away are they. Sight is a distance check, a field-of-view angle check, and a raycast so walls actually block line of sight. Hearing is a radius that grows when the player sprints. The senses also remember the last known position, which is what the Search state goes to look at.

Patrol

The default state. The enemy walks a loop of waypoints on the NavMesh, with a short idle pause at each one so patrols don't look mechanical. This is the M4 waypoint loop grown up: the same arrival check, but with randomized pauses and a walk animation driven from the agent's velocity.

Chase

Run toward the player's current position, re-pathing on a short timer rather than every frame so the NavMesh isn't hammered. The enemy keeps a lost-sight timer: if the player breaks line of sight and stays hidden for a few seconds, Chase gives up and hands over to Search.

Attack

Stop moving, face the player, and trigger the attack animation. The damage is applied by an animation event at the frame the hit lands, not when the state starts, so blocking or stepping back at the right moment works. A cooldown timer stops the enemy from attacking every frame, and if the player moves out of range during the cooldown the enemy drops back to Chase.

Under the hood

Facing the player is a smoothed rotation toward the target each frame (the NavMeshAgent's own rotation is switched off while attacking so it doesn't fight the turn). The attack trigger and the "hit" animation event are the two points where the state machine and Mecanim meet, and both came straight from what M1 taught about animation events.

Search

Go to the last place the player was seen, look around for a moment, then return to Patrol. If the senses pick the player up again at any point, Search jumps straight back to Chase. This state is what makes hiding feel like a real option instead of an exploit.

Retreat

When health drops below a threshold, the enemy disengages: it picks a point away from the player (or back toward its spawn), runs there, and recovers before returning to Patrol. Enemies that back off and come back read as far smarter than enemies that fight to the death every time.

Dead

Reachable from any state. It disables the agent and the senses, plays the death animation, and stops the enemy from ever transitioning again. Handling death as a state rather than a flag meant no other state needed a "but what if we're dead" check.

Tuning and debugging

  • Every number the behaviors depend on (sight range and angle, hearing radius, attack range and cooldown, give-up time, retreat health threshold, walk and run speeds) is a public field, so each enemy type could be tuned in the Inspector without touching code.
  • Gizmos draw the vision cone, hearing radius and the current state's name above each enemy in the Scene view, which turned "why is it doing that?" into something I could see.
  • Because all transitions go through one method, logging it gave a readable trace of every decision an enemy made during a playtest.

The ladder

The four milestones

Each milestone came as a written brief and a starter Unity project with two human characters and two cartoon "minions". The job was to extend it, build it, and submit a playable executable. The briefs read like a tour of a game engine, and that's what they were.

M1

Character animation

Making a character move and look right while moving. The whole milestone is about the gap between those two things.

What I built
  • Compared a character driven by code (programmatic motion) with one driven by its animation data (root motion), and saw why the first one's feet slide during turns.
  • Extended the root-motion character with run animations in a 2D blend tree, so walking blends smoothly into running in any direction.
  • Added speed scalars to the controller: the animator's playback speed, plus scaling the per-frame root movement and rotation with LerpUnclamped, so the character could be snappier without losing planted feet.
  • Hand-animated the minion with keyframes and curves: a hop and a twist on top of its forward motion, with matching left/right turn versions.
  • Added animation events that fire a footstep sound at the right frames, through the project's event system.
  • Used Animator.MatchTarget to slide the character into position before pressing a button, and inverse kinematics (OnAnimatorIK) so the hand reaches the actual button and the head looks at it.
Skills
  • Mecanim state machines, transitions, exit times and blend trees.
  • Root motion vs programmatic control, and the hybrid most real games use.
  • Keyframe animation, tangent curves, partial keyframes, animation events.
  • Target matching and IK for interactions with the world.
M2

Physics simulation

A scene full of small physics experiments, each demonstrating one feature of Unity's rigidbody engine, all visible from the camera the moment the game starts.

What I built
  • Stacked spheres that topple and ring a sound on collision, by reporting OnCollisionEnter as an event the audio manager listens for.
  • A second stack on a physics layer that ignores itself, so the spheres fall straight through one another (the collision matrix in action).
  • A compound collider: a stone fox mask built from several invisible primitive colliders so it tips over and lands on its nose convincingly, without a mesh collider.
  • A hanging chain of five rigidbodies linked with configurable joints, swinging at start.
  • A kinematic elevator animated with Mecanim and set to "animate physics", carrying a ball up and dropping it, over and over.
  • A weeble that can't be knocked over, by moving its center of mass low into a capsule.
  • Friction and bounce materials: a box that grips a ramp, one that slides down it, and a ball that bounces for a long time.
  • A ragdoll from the Ragdoll Wizard that flops over a hurdle.
  • An autonomous "click beetle": a script that applies random impulses and torques in FixedUpdate at random intervals, only while grounded.
Skills
  • Rigidbodies, colliders, triggers and collision callbacks.
  • Physics layers, physics materials, joints, kinematic bodies and tunneling fixes.
  • Applying forces from code and the difference between Update and FixedUpdate.
M3

Game menus and collectables

The parts that turn a scene into a game: a front door, a pause screen, things to pick up, and objects that react to you.

What I built
  • A start-menu scene that uses the level itself as a backdrop, blurred and grained with post-processing, with Start and Exit buttons wired to scene loading and quitting.
  • An in-game pause menu on a canvas group: Escape fades it in, blocks input, and freezes time with Time.timeScale; Restart and Quit buttons reuse the same scripts.
  • A collectable ball built on a trigger collider. It only responds to the character that carries a BallCollector component, tells that component it was collected, fires a sound event and removes itself.
  • A prefab that animates when the player gets close and resets when they leave, driven by a Mecanim state machine I built, with three copies placed in the level.
Skills
  • Unity UI: canvases, panels, anchors, the canvas scaler and why pixel offsets break at other resolutions.
  • Scene management and the gotchas of pausing (timeScale survives scene loads).
  • Trigger-based interaction, prefabs, and an event system that decouples what happened from who reacts.
  • Post-processing volumes and layers.
M4

Artificial intelligence

Taking the keyboard away from the minion and giving it a brain: a navigation mesh, a patrol route, and the ability to intercept a moving target.

What I built
  • Stripped the player-control scripts from a minion, added a NavMeshAgent, baked a NavMesh over the level and tuned the agent's size, speed and turn rate to it.
  • A waypoint loop over five visible markers, advancing when the agent arrives (checking remainingDistance only once no path is pending, so it doesn't skip ahead).
  • Drove the hop animation from the agent's actual velocity, so the minion steps when it moves and idles when it stops.
  • A procedural state machine with two states, patrol and intercept, looping forever.
  • Intercept by prediction: read the moving target's velocity, estimate a lookahead time from the distance, extrapolate where it will be, clamp the lookahead and raycast against the NavMesh so the prediction never leaves walkable ground. A tall marker shows the predicted point every frame.
Skills
  • NavMesh baking and agents; steering without writing steering.
  • State machines for behavior, and why they pay off as behaviors multiply.
  • Position prediction and pursuit, with the safety checks that keep it on the map.

Looking back

What it taught me

  1. Feel is engineering. Whether a character's feet slide or a jump feels floaty comes down to concrete choices: root motion or not, which blend tree, what friction. Those are tunable, testable decisions, not magic.
  2. Decouple with events. The starter project's event manager, where a collision raises an event and an audio manager answers it, is the pattern that kept the team project from becoming one giant script.
  3. Let the engine do the steering. A NavMesh plus a few lines of prediction beat anything I could hand-write for moving a character around a level. The interesting work is in deciding where to go.
  4. Ship builds early. Every milestone was graded on an executable, not the editor. Things that work in the editor and break in a build (missing scenes, paused time, UI scaling) only show up if you build often.
