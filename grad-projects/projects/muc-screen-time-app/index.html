An iPhone app that watches how you use your phone

Our team built an iOS app that connects three signals most people never see together: which apps you spend time in, whether you're moving or sitting still, and how stressed you are. I owned the monitoring pipeline, the part that gets usage data out of iOS despite Apple's privacy walls, and the reports built on it.

The 30-second version

  • What it is: a SwiftUI iPhone app with four tabs: Home, Activity, a test bench, and Settings. The Activity tab asks for Screen Time permission, lets you pick apps to watch, and shows your usage as a timeline of sessions.
  • The hard part: iOS does not let an app read screen-time data directly. I built the pipeline around Apple's DeviceActivity framework: a background extension that wakes up on usage events and passes them to the app through a shared container.
  • Also: a Core Motion tracker that logs when the phone's owner is walking, running, driving or still, a 15-minute test mode with a live countdown and report, and a demo-data mode so the UI could be developed and shown without a provisioned device.
  • Team: three of us. I wrote the monitoring and report code and the setup guides the others used to get the extensions building on their Macs.
Background

The idea

Screen Time tells you that you spent three hours on your phone. It doesn't tell you whether those were three hours on the couch or three hours walking between meetings, or how you felt at the end of them. The course was about ubiquitous computing: using the sensors people already carry to understand their behavior. Our app put phone usage, physical activity and a stress estimate side by side so the connections become visible.

The constraint

Apple's privacy wall

This project had one problem that shaped everything else. Apple treats screen-time data as among the most sensitive on the device. An app can show the user a Screen Time chart, but the chart is drawn by a separate, sandboxed extension that the app itself cannot read from. The numbers never cross into your code.

What Apple does allow is event-based monitoring. An app can ask for permission under the Family Controls framework, let the user pick apps with a system picker (your code receives opaque tokens, not app names), and schedule a monitor. iOS then wakes a small extension of your app when things happen: a monitoring window starts or ends, or usage of the chosen apps crosses a threshold you set. That is the door I built the pipeline through.

What this meant in practice

Nothing worked in the simulator; every test needed a real iPhone with Screen Time on, a developer account, three entitlements, and an App Group shared by the app and its extension. Half of the engineering effort was configuration, which is why I ended up writing three setup guides for the team.

Architecture

How the pipeline works

Ask for permission

The app requests Family Controls authorization through AuthorizationCenter. Until the user approves in the system sheet, every other control stays disabled and the screen explains why.

Under the hood

Authorization is asynchronous, so the manager is an ObservableObject whose published state drives the UI, and the request runs with Swift's async/await. The status is re-checked on every launch because the user can revoke it in Settings at any time.

Pick what to watch

A system-provided picker lets the user choose apps and categories. The app receives a FamilyActivitySelection, which is a set of opaque tokens: it can pass them to the monitor, but it cannot see which apps they are.

Under the hood

The selection has to reach the extension, which runs as a separate process. I serialize it into the App Group's shared UserDefaults so the extension can load it when iOS wakes it up. The App Group identifier has to match in both targets' entitlements, in the provisioning profiles and in the developer portal, or the write silently falls back to a private store and nothing arrives. That one mismatch cost the team a full day, which is why it got its own setup guide.

Schedule the monitor

A DeviceActivitySchedule defines the window (a repeating daily interval for normal use, a 15-minute one for the test mode) and a DeviceActivityEvent sets a usage threshold on the selected apps. DeviceActivityCenter.startMonitoring hands both to iOS.

The extension wakes up

iOS launches the monitor extension and calls its callbacks: intervalDidStart, intervalDidEnd, eventDidReachThreshold, and their warning variants. Each callback stamps the moment and appends an event record to the shared store. A threshold event closes any open usage session; an interval start opens the day.

Under the hood

The extension has seconds to run and no UI, so it does the minimum: load the selection, build a small dictionary (type, timestamp, activity name), append it to a JSON array in the shared store, and return. Everything heavier (grouping, totals, charts) happens later in the app. When the shared store isn't reachable, it logs the failure rather than crashing, because a crashing extension gets throttled by the system.

Turn events into sessions

Back in the app, the manager polls the shared store on a timer, reads the event log and folds it into AppUsageSession values: an app, a start time, an end time, a duration. The Activity tab lists them newest first, and the Report screen summarizes them with totals and the system events that happened in between.

Demo mode

Because real data needs a provisioned iPhone, I added a "fake monitor" path that generates realistic sessions through the same code, with every screen clearly labelled FAKE. That let the team design the UI, record demos and present without waiting on entitlements.

Second signal

Movement tracking

Phone usage alone is half the picture, so the app also tracks what the body is doing. Apple's Core Motion framework classifies the phone's movement into stationary, walking, running, cycling and automotive, using the motion coprocessor, so it costs almost no battery.

My BackgroundActivityTracker subscribes to those updates, de-duplicates them (Core Motion reports often, but the classification rarely changes) and logs each transition with a timestamp and confidence. In the report, a usage session that overlaps a long "stationary" stretch reads very differently from one that overlaps "walking". One teammate's stress tracker, which used simulated heart-rate data, was the third signal on the same timeline.

Under the hood

CMMotionActivityManager.startActivityUpdates delivers CMMotionActivity objects on a queue. I keep the last classification and only log when it changes or the confidence improves, which turns a stream of hundreds of updates into a readable list of a dozen transitions per hour. Availability is checked first; the simulator and some older devices have no motion coprocessor.

Process

Working as a team

Three people, one Xcode project, and frameworks none of us had used before. A few things that kept it moving:

  • One folder per person. Each of us owned a folder under the app target and a test view in a shared "Test" tab, so we could build and try features independently before wiring them into the main screens.
  • Setup guides as documentation. Getting the extension, the App Group and real data working involved a dozen non-obvious steps across Xcode, the developer portal and the phone. I wrote them down as three markdown guides in the repo, including the exact error messages and what each one meant.
  • Demo data as a contract. The fake-data generator produced the same model types as the real pipeline, so teammates could build against it without my part being finished.
Looking back

What it taught me

  1. Read the platform's rules before designing. A week of trying to read screen-time data directly would have been wasted. Understanding why Apple blocks it pointed straight to the event-based design that worked.
  2. Processes that share nothing need a contract. The app and its extension communicate only through the App Group store, so the event format became the most important interface in the project.
  3. Configuration is engineering. Entitlements, bundle IDs, provisioning and App Groups broke the build more often than code did. Writing the guides turned that from a recurring emergency into a checklist.
  4. Build the fake path first. The demo-data mode unblocked the whole team and doubled as a test harness for the real one.
Reference

Key terms

Family Controls
Apple's framework for apps that manage or observe device usage. Needs explicit user approval and a special entitlement.
DeviceActivity
The framework that schedules monitoring windows and wakes an extension on usage events.
app extension
A small separate process bundled with an app that iOS runs on its own schedule, without a UI.
App Group
A shared container that lets an app and its extensions read the same files and defaults.
opaque token
What the app gets instead of an app's name when the user picks apps: usable for monitoring, unreadable by code.
Core Motion
The framework that reports the phone's movement classification from the motion coprocessor.
SwiftUI
Apple's declarative UI framework; views re-render automatically when published state changes.
entitlement
A signed capability flag the app must carry to use a restricted framework.
