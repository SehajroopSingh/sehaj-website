Sharing one machine between eight virtual ones

A cloud server runs many virtual machines on one box. Someone has to decide which VM gets which CPU core, and how much memory each one holds, as their needs change minute to minute. For this project I wrote the two programs that make those decisions, and tested them against real KVM virtual machines.

The 30-second version

  • Setup: one Linux host with 4 physical cores runs 8 virtual machines. Each VM has 1 virtual CPU and starts with a few hundred MB of memory.
  • Program 1, the vCPU scheduler: every few seconds it measures how busy each VM is and pins VMs to cores so that all four cores carry the same load. Once balanced, it leaves things alone.
  • Program 2, the memory coordinator: every few seconds it checks how much free memory each VM has. VMs that are running out get more; VMs that are hoarding give some back. The host is never drained.
  • Result: in the recorded tests, the scheduler balanced 8 VMs onto 4 cores with a single re-pin and held every core within a few percent of the others. The coordinator grew a hungry VM from 256 MB to 1.2 GB in 100 MB steps and shrank it back when the load went away.
Background

The setup: one host, eight guests

A virtual machine (VM) is a computer running inside another computer. The real machine is called the host; the VMs are guests. The piece of software that creates the illusion is the hypervisor. On Linux that's KVM, and the guests here are ordinary Ubuntu VMs named aos_vm1 through aos_vm8.

Each guest thinks it owns a CPU. It doesn't. Its "virtual CPU" (vCPU) is a thread on the host that the hypervisor runs on one of the real cores (pCPUs). The same goes for memory: the guest sees a block of RAM, but the host decides how much of it is real at any moment.

My two programs sit outside the VMs, in the host's user space, and talk to the hypervisor through libvirt, the same C library that tools like virsh and virt-manager use.

Why this matters

This is a small version of what every cloud provider does all day. Over-subscribe a host (more vCPUs than cores, more promised memory than RAM), then shuffle resources around so nobody notices. The interesting part is doing it from the outside, with only the statistics the hypervisor exposes.

Part 1

The vCPU scheduler

The problem

Eight vCPUs, four cores. If the hypervisor happens to put all eight on core 0, one core runs flat out while three sit idle. Every VM gets an eighth of a core instead of half of one. The job of the scheduler is to pin each vCPU to a core so the load is even, and to stop fiddling once it is.

Two words from the project spec drove the design:

  • Balanced: no core is noticeably busier than the others. The measure is the standard deviation of the four cores' utilization; under 5 counts as balanced.
  • Stable: once balanced, don't keep moving vCPUs around. Every re-pin costs a cache flush and a scheduling hiccup inside the guest, so a scheduler that "fixes" a balanced system every interval is worse than one that does nothing.

The loop, step by step

The program takes one argument, the interval in seconds, and repeats the same six steps until you press Ctrl-C.

Connect to the hypervisor

Open a connection to the local KVM instance. Everything else goes through this handle.

Under the hood

virConnectOpen("qemu:///system"). The system URI means the host-wide daemon, which is the one that owns the VMs launched by root or virt-manager. The connection stays open for the life of the program.

List the running VMs

Ask libvirt for every active guest. The scheduler should work for any number of VMs, so nothing is hard-coded.

Under the hood

virConnectListDomains returns the IDs of running domains; virDomainLookupByID turns each into a handle. VMs can come and go between intervals, so the list is rebuilt every pass.

Measure each vCPU

For every VM, read two things: how much CPU time it has used, and which physical core it's currently on.

Under the hood

The CPU time comes from virDomainGetCPUStats as a cumulative counter in nanoseconds since the VM booted, not as a percentage. Converting it takes two samples:

# one interval of real time is interval × 10⁹ ns
usage% = (cpu_time_now − cpu_time_last) / (interval × 1e9) × 100

A vCPU that is busy for the whole interval comes out near 100%. The current core comes from virDomainGetVcpus, which fills a virVcpuInfo struct whose cpu field is the pCPU the vCPU last ran on.

Add it up per core

Sum the usage of every vCPU pinned to each core. Now there are four numbers, one per pCPU, and that is all the decision needs.

Decide

Three cases, checked in order:

  • First pass: no history yet, so deal the vCPUs out round-robin: VM 1 to core 0, VM 2 to core 1, and so on, wrapping around. This instantly fixes the "everything on core 0" case.
  • Every core is within a band around the target load: do nothing. This is the stability rule.
  • Otherwise: re-plan. Walk through the vCPUs and give each one to whichever core currently has the least load, adding its usage to that core's tally as you go. A greedy pass like this gets within a few percent of optimal for workloads this size.
Under the hood

The target load per core is the total vCPU usage divided evenly across the cores. In my submission the band was ±10% of that target. Wider bands tolerate noisy readings but let real imbalance persist; narrower bands react faster but risk re-pinning on noise. I settled on 10% after watching the monitor flip-flop at 5%.

load[c] = Σ usage of vCPUs on core c

if first_run:
    pin vm_i → pcpu (i mod num_pcpus)          # round robin
elif every load[c] within ±10% of target:
    return                                  # stable: leave it alone
else:
    for vm in vms:                            # greedy rebalance
        c = argmin(load)
        pin(vm, c)
        load[c] += usage[vm]

Act, then sleep

Apply the new pins through libvirt, sleep for the interval, and go back to step 2.

Under the hood

virDomainPinVcpu(domain, vcpu, cpumap, maplen) takes a bitmap: bit i set means the vCPU may run on pCPU i. Pinning to a single core is a one-byte map with one bit set (1 << core). The call changes the affinity of the host thread that backs the vCPU, so the Linux scheduler moves it immediately. A SIGINT handler flips an exit flag so the loop ends cleanly and the connection is closed.

Part 2

The memory coordinator

The problem

A VM's memory is set when it boots. If VM 1 then starts a program that needs more, it has nowhere to get it from, while VMs 2 through 8 sit on memory they aren't using. The coordinator's job is to move memory from VMs that don't need it to VMs that do, without ever starving a guest or the host.

The mechanism that makes this possible is the balloon driver. It's a small driver inside each guest that can "inflate", grabbing pages of guest memory and handing them back to the host, or "deflate", returning them to the guest. From the host, inflating the balloon looks like shrinking the VM.

What the coordinator can see

For each VM, libvirt reports a handful of memory statistics. I used two: actual, the current balloon target (how much memory the VM has right now), and unused, how much of that the guest reports as free. From the host side it also reads the host's own free memory. That's enough to tell who is starving, who is hoarding, and whether the host can afford to give.

Under the hood

Memory stats come from virDomainMemoryStats, which returns tagged values: VIR_DOMAIN_MEMORY_STAT_ACTUAL_BALLOON, …_UNUSED, …_AVAILABLE and others, all in kilobytes. The guest only reports them if collection is switched on with virDomainSetMemoryStatsPeriod; without that call the "unused" field never appears. Host free memory comes from virNodeGetMemoryStats. Resizing is a single call, virDomainSetMemory(domain, kilobytes), which sets the new balloon target.

The rules

Each interval, the coordinator walks through the VMs and applies one of two rules. The thresholds came from the project's safety requirements plus some tuning against the test workloads.

If a VM has…It is…ActionGuard
< 90 MB unusedstarving+100 MBonly if the host keeps ≥ 200 MB free; otherwise borrow 100 MB from a VM with > 150 MB unused
200–250 MB unusedhoarding a little−30 MBnever leaves a guest with less than 100 MB unused; shrinks in steps, not all at once
250–300 MB unusedhoarding−70 MB
> 300 MB unusedhoarding a lot−100 MB
90–200 MB unusedcomfortablenothingthe dead zone that keeps the system from oscillating

Two things in that table are deliberate. The dead zone between 90 and 200 MB means a VM that just received memory isn't immediately asked to give it back. And reclaiming happens in graduated steps, because yanking 500 MB from a guest in one go can push it into swapping before its kernel has time to react; the spec explicitly asked for gradual release.

Under the hood 
host_free = node_free_memory_mb()
for vm in running_vms:
    actual, unused = memory_stats(vm)        # MB
    if unused < 90:                            # starving
        if host_free >= 200:
            set_memory(vm, actual + 100)
        else:                                  # host is tight: rob a hoarder
            donor = first vm with unused > 150
            set_memory(donor, donor.actual − 100)
            set_memory(vm, actual + 100)
    elif unused > 200:                         # hoarding: give back gradually
        step = 100 if unused > 300 else 70 if unused > 250 else 30
        set_memory(vm, actual − step)
sleep(interval)

The borrow-from-a-hoarder branch is what keeps the host alive when every VM wants memory at once: instead of handing out the host's last 200 MB, the coordinator shuffles memory between guests.

Verification

How I tested it

You can't unit-test a hypervisor policy on a laptop, so the test setup was a real one: an Ubuntu virtual machine in Azure with nested virtualization turned on, running KVM, with eight guest VMs cloned from one image. For development I used a Vagrant box with the same layout.

Each test was a three-terminal affair:

  1. Start script to record everything printed in the terminal to a log file.
  2. Run the course's monitor, which samples every VM through libvirt once per interval and prints the pin map and usage (or the memory numbers) in a fixed format. It also launches the workload inside the guests over SSH.
  3. In another terminal, start my scheduler or coordinator with a 2-second interval and let it run until the monitor's samples settle.

Six recordings came out of this, three for CPU and three for memory, and every chart on this page is drawn from them. Here is what the monitor printed around the moment the test-2 workload kicked in:

The three CPU scenarios were: already balanced (the scheduler should do nothing), everything on core 0 (it should spread them out), and a mix of heavy and light VMs placed at random (it should pair heavy with light). The three memory scenarios were: one VM hungry, all VMs hungry, and VMs that have been hungry and then go idle.

Looking back

What I'd do differently

The programs passed their tests, but reading the code a year later I can see four things I'd change.

  1. Measure usage per interval, not since boot. My submitted scheduler compared the VMs' cumulative CPU-time counters directly. That works when every VM booted at the same time and runs a similar load (which the tests did), but a VM that was busy an hour ago would look "busy" forever. The fix is the subtraction shown in step 3: keep the previous sample and use the difference.
  2. Derive the target from the counts, not an assumption. The balance band was built around "two vCPUs per core", which is true for 8 VMs on 4 cores and false for anything else. The target should simply be total usage divided by the number of cores.
  3. Sort before the greedy pass. Assigning the biggest loads first (the classic longest-processing-time rule) gets closer to optimal than walking the VMs in ID order, especially with mixed heavy and light workloads.
  4. Add hysteresis to the memory rules. The dead zone helps, but a VM sitting right at 90 MB unused can be topped up every single interval. Requiring two consecutive readings below the threshold would cut needless balloon churn.
Reference

Key terms

hypervisor
Software that runs virtual machines. KVM is Linux's built-in one; QEMU provides the virtual hardware.
libvirt
A C library and daemon that gives one API for managing VMs on any hypervisor. My programs are libvirt clients.
vCPU / pCPU
A virtual CPU as seen by a guest, and a physical core on the host. Several vCPUs can share one pCPU.
pinning
Restricting a vCPU to a specific pCPU (or set of them). Without pinning, the host's scheduler moves vCPUs around freely.
balloon driver
A driver inside the guest that can hand memory back to the host (inflate) or take it back (deflate) on request.
actual / unused
The two memory statistics I used: how much memory a VM currently holds, and how much of that its kernel reports as free.
standard deviation (σ)
How spread out the four cores' usage numbers are. Zero means perfectly even; the spec counted under 5 as balanced.
interval
How often the programs wake up, measure and act. The tests used 2 seconds.
