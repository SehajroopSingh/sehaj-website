Three pieces of an operating system, written inside one

InfOS is a small research kernel built for teaching: it boots in an emulator, and the parts a student would normally only read about are left as holes to fill. I filled three of them in C++: the scheduler that decides which thread runs, the allocator that hands out physical memory, and the cache that sits between the filesystem and the disk.

The 30-second version

  • Scheduler: four run queues, one per priority level. The CPU always goes to the highest non-empty queue, and threads inside a queue take turns.
  • Buddy allocator: physical memory is handed out in power-of-two page blocks. Big free blocks split in half on demand; freed halves merge back with their "buddy" so memory doesn't fragment.
  • Block cache: a 64-slot cache in front of the disk driver. Repeated reads of the same 512-byte block are served from memory, and every access is logged as a hit or a miss.
  • Why it's hard: all three run inside the kernel. There is no debugger to lean on, a wrong pointer freezes the whole machine, and every data structure has to be written by hand because there is no standard library.
Background

What InfOS is

InfOS is a teaching operating system written in C++. It has everything a real kernel has in miniature: threads and processes, a virtual memory system, a filesystem, device drivers, and a tiny shell. It runs under QEMU, a machine emulator, so you can boot it, break it and reboot it in seconds.

Each task hands you an interface and an empty implementation. The scheduler, for example, must be a class that answers one question whenever the kernel asks: which thread should run next? Everything else, from timers to context switching, already exists. The work is in getting the policy right, and in writing it without any of the conveniences of user-space code.

Task 1

A priority scheduler

Dozens of threads want the CPU: the shell, a program the user launched, background daemons, and the occasional time-critical thread. InfOS tags every thread with one of four priorities, from realtime down to daemon. The scheduler's job is to honor those tags without starving anyone forever.

How it works

One queue per priority level

Four linked lists, one for realtime, interactive, normal and daemon threads. When a thread becomes runnable, the kernel calls add_to_runqueue and I append it to the list for its priority; when it blocks or exits, remove_from_runqueue takes it out.

Under the hood

There is no std::vector or std::list in a kernel. InfOS ships its own minimal List<T>, a singly linked list with append, remove, first and count, and that is what the queues are built from. Priorities arrive as an enum, which I clamp into the range of queues so an unexpected value can never index past the array.

Pick the highest non-empty queue

Every time the kernel needs a decision (a timer tick, a thread blocking, a new thread appearing) it calls pick_next_entity. I check the queues from realtime downward and take the first one that has anything in it. A realtime thread therefore always wins over an interactive one, and so on down.

Rotate within the queue

The chosen thread is moved from the head of its queue to the tail before it runs. Next time that queue is picked, the following thread gets its turn. That's round-robin: every thread at the same priority gets an equal share of the CPU.

Under the hood

Rotation is a remove followed by an append on the same list. Because the scheduler runs with interrupts disabled, no lock is needed around it, but the operation still has to be cheap: this code runs on every single timer tick.

pick_next_entity():
    for level in [realtime, interactive, normal, daemon]:
        if queue[level] is not empty:
            t = queue[level].first()
            queue[level].remove(t); queue[level].append(t)   # rotate
            return t
    return idle_thread

Keep the lower levels alive

Strict priority has a known flaw: as long as one interactive thread keeps running, normal and daemon threads never get a turn. In an extended version of the scheduler I tracked how many consecutive slices each level had received and, past a limit, let a lower queue run one slice before returning to strict order. That keeps background work moving without letting it slow the foreground down.

Why this matters

Linux's scheduler is far more sophisticated, but the shape is the same: classes of threads ranked by importance, fairness inside a class, and explicit guards against starvation. Writing the simple version by hand is the fastest way to understand why the complicated versions look the way they do.

Task 2

A buddy page allocator

The kernel manages physical memory in 4 KB pages. Drivers and the virtual memory system ask for contiguous runs of pages: 1, 2, 4, 8, up to thousands at a time. Handing those out naively leaves memory full of holes too small to use. The buddy system is the classic answer, and it's what Linux uses too.

The idea: every free block is a power of two pages long, and every block has exactly one "buddy", the other half of the block it was split from. Need 2 pages but only an 8-page block is free? Split it into two 4s, split one 4 into two 2s, hand one 2 out. Free it later, and if its buddy is also free, they merge back into a 4, which may merge into an 8. Fragmentation heals itself.

How it works

Free lists by order

An array of linked lists, indexed by order. Order 0 holds free single pages, order 1 holds free pairs, order 2 holds free blocks of four, and so on up to the largest block the kernel allows. Each list is kept sorted by address, which makes buddy lookups and debugging far easier.

Under the hood

InfOS describes each physical page with a PageDescriptor struct, and the free lists are threaded through those descriptors rather than allocated separately, because the allocator can't call an allocator. A block of order n is represented by the descriptor of its first page. A block is only valid at order n if its page-frame number is a multiple of 2ⁿ, and I check that alignment on every operation and panic loudly if it's wrong; in a kernel, an early panic beats silent corruption.

Allocate: find, split, hand out

For a request of order k, scan upward from order k for the first non-empty list. Take that block. While it is bigger than needed, split it: the lower half stays with us and drops one order, the upper half goes onto the free list one order down. Stop when the block is the requested size.

Free: insert, then coalesce

Put the block back on its order's list. Then look up its buddy. If the buddy is free and the same order, remove both and insert the merged block one order up. Repeat until the buddy is in use or the top order is reached.

Under the hood

Finding a buddy costs one XOR. If a block starts at page-frame number pfn and has order n, its buddy starts at pfn ^ (1 << n): flip the single bit that distinguishes the two halves. The merged block always starts at the lower of the two addresses.

free_pages(block, order):
    insert(block, order)
    while order < MAX_ORDER:
        buddy = pfn(block) ^ (1 << order)
        if buddy not free at this order: break
        remove(block, order); remove(buddy, order)
        block = min(block, buddy); order += 1
        insert(block, order)

Boot-time setup and reserved ranges

At boot the allocator is told which page ranges exist and which are already taken (the kernel image, device memory). Inserting a free range means carving it into the largest aligned power-of-two blocks that fit; reserving a range means splitting down until the exact pages can be marked used. Both are the same split logic, applied at startup.

Task 3

A block cache for the disk

Every file read ends up as a request for 512-byte blocks from the ATA disk driver, and the emulated disk is slow compared with memory. Filesystems also ask for the same blocks over and over: directory entries, inode tables, the start of a file. A block cache keeps recently used blocks in RAM so most of those requests never reach the disk.

How it works

A fixed table of slots

Sixty-four slots, each holding a block number, a 512-byte buffer and a "last used" stamp. The size is a compile-time constant so the graders could rebuild the kernel with different cache sizes and check that behavior scaled sensibly.

Hook the driver's read

The ATA driver's block-read function was changed to ask the cache first. On a hit, the slot's buffer is copied to the caller and the access counter updated. On a miss, the driver does the real read, the cache stores a copy, and the result is returned. Either way one line is logged: [CACHE HIT] or [CACHE MISS] with the block offset.

Under the hood

Block offsets arrive in bytes, so the block number is offset / 512, and a multi-block request is handled one block at a time so that a partially cached run still gets partial hits. Copies use the kernel's own memcpy; the cache buffers are allocated once at init time, because allocating inside the read path of a disk driver is asking for deadlock.

Evict the least recently used block

When all 64 slots are full and a miss arrives, the slot with the oldest "last used" stamp is overwritten. That's LRU, the policy that best matches how filesystems access disks: whatever was touched most recently is most likely to be touched again.

Under the hood

With only 64 slots a linear scan for the oldest stamp is cheaper than maintaining a linked LRU list, and far less error-prone in kernel code. I started down the linked-list road (a move_to_front on InfOS's list type) and backed out when the scan turned out to be both simpler and fast enough.

Looking back

What it taught me

  1. Kernel code has no safety net. A null pointer doesn't throw; it halts the machine. I learned to assert alignment and ownership at every boundary and to let the kernel panic early with a useful message.
  2. Data structures are yours to write. No STL, no allocator you can call from inside the allocator. Threading free lists through the page descriptors themselves was the first time I really understood intrusive data structures.
  3. Policy and mechanism are separate. The kernel provided the mechanism (context switches, disk I/O). The tasks were all policy: which thread, which block, which page. That separation is what makes a kernel testable at all.
  4. Simple beats clever under constraints. The linear LRU scan over 64 slots and the XOR buddy lookup both replaced fancier designs I started with. In the kernel, fewer moving parts is a feature.
Reference

Key terms

InfOS
A small C++ teaching kernel that boots under QEMU. Students implement components behind fixed interfaces.
run queue
The list of threads that are ready to run. This scheduler keeps one per priority level.
round-robin
Taking turns: the thread that just ran goes to the back of the line.
page / order
A 4 KB unit of physical memory, and the power-of-two size of a block: order n = 2ⁿ pages.
buddy
The other half of the block a block was split from. Found with one XOR on the page number.
coalesce
Merging two free buddies into one bigger free block.
block cache
RAM copies of recently read disk blocks, so repeated reads skip the disk.
LRU
Least recently used: when the cache is full, drop the block that has gone longest without being touched.
