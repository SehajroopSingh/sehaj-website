Cryptography: when correct maths meets bad choices

RSA is mathematically sound, yet real systems keep breaking it. I implemented RSA from first principles and then the classic attacks on weak deployments, which made it very clear that crypto fails in the details, not the theory.

The 30-second version

  • Did: attacks on deliberately weak RSA setups in Python, showing that the maths of RSA can be perfect while the way it is used is broken.
  • Covered: how RSA works from first principles (primes, modular arithmetic, key generation) and the classic implementation mistakes: keys that are too small, primes reused or chosen badly, and exponents that are too small for the message.
  • Learned: why "don't roll your own crypto" is real advice, and how much security rests on details like how primes are generated.
Background

RSA in one paragraph

RSA picks two large secret primes, multiplies them into a public modulus, and derives a public and a private exponent from them. Anyone can encrypt with the public key; only the holder of the primes can decrypt. Its security rests on one assumption: that factoring the modulus back into its primes is infeasible. Every attack in this project is a way that assumption quietly stops being true.

The attacks

Where good maths meets bad choices

Keys that are too small

A modulus short enough can simply be factored with ordinary computing power, and once you have the primes you have the private key.

Primes shared between keys

If two different public keys accidentally share a prime, a single greatest-common-divisor computation reveals it, and both keys fall. This has happened at internet scale with badly seeded devices.

Primes too close together

If p and q are nearly equal, Fermat's factorisation method finds them quickly from the square root of the modulus.

Exponents and messages that are too small

With a tiny public exponent and no padding, some messages can be recovered with nothing more than an integer root.

The pattern

None of these attacks break RSA itself. They exploit the gap between the textbook algorithm and a real deployment: randomness, key sizes, padding. That gap is where most real cryptographic failures live.

Defence

How to defend against it

Use vetted libraries
Let well-reviewed libraries generate keys and handle padding; never implement the primitives yourself.
Modern parameters
2048-bit or larger RSA keys, or modern elliptic-curve schemes.
Proper padding
OAEP for encryption and PSS for signatures, never raw "textbook" RSA.
Good randomness
Key generation must use a cryptographically secure random source, seeded properly.
Looking back

What it taught me

  1. Security lives in the details. The algorithm was fine every time; the parameters were not.
  2. Small maths, big consequences. A one-line GCD can break keys that look strong.
  3. Trust the libraries. Understanding the attacks is exactly why I would never hand-roll crypto in production.
Reference

Key terms

RSA
A public-key system whose security rests on the difficulty of factoring large numbers.
modulus
The public product n = p × q.
GCD
Greatest common divisor; reveals a shared prime between two moduli.
Fermat factorisation
A method that quickly factors n when its two primes are close together.
padding (OAEP)
Randomised structure added before encryption so textbook attacks fail.
