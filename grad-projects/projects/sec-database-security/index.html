Database security: through the front door and the side door

Databases leak in two very different ways: queries built carelessly from user input, and aggregate statistics that reveal more than anyone intended. I explored both against a SQL Server lab database, and both changed how I think about building data products.

The 30-second version

  • Did: two kinds of attack on a SQL Server database: SQL injection through an application's inputs, and inference attacks that recover private records from "safe" aggregate statistics.
  • With: T-SQL and a small web front end, in a lab virtual machine.
  • Learned: that databases leak through both the front door (bad query building) and the side door (statistics that reveal more than intended).
Background

Two ways data escapes

SQL injection happens when an application builds a query by gluing user input into SQL text. Input that contains SQL syntax changes the meaning of the query, so a login check or a search can be turned into something that reads, or changes, data it was never meant to touch.

Inference attacks are subtler. A database may hide individual rows and only answer aggregate questions such as counts and averages. But by asking several overlapping questions and comparing the answers, you can often narrow the result down to a single person and learn their value. This is exactly the problem that privacy techniques like differential privacy were invented to solve.

The work

What I explored

Find the injectable inputs

Identify where user input reaches a query unsafely, and how the application responds to malformed input.

Understand the query

Reason about the SQL the app must be running and how input changes its logic, using the database's own structure where the app exposes it.

Infer without seeing

Combine permitted aggregate queries, each harmless alone, until they pin down a specific hidden record.

Write it up precisely

Record each finding in a structured format that a grader, or a security team, could verify.

Defence

How to defend against it

Parameterised queries
Input is passed as data, never as SQL text, which removes injection entirely.
Least privilege
The app's database account should only be able to do what the app needs.
Query-set restrictions
Refuse aggregates over very small groups and audit overlapping queries.
Differential privacy
Add calibrated noise to statistics so no individual can be singled out.
Looking back

What it taught me

  1. Never build SQL with strings. Parameterisation is a one-line habit that removes a whole category of breach.
  2. Aggregates are not anonymous. Overlapping statistics can rebuild individual records, which matters for any analytics product.
  3. Data and privacy are one topic. This project connected straight back to my data-science work.
Reference

Key terms

SQL injection
User input altering the structure of a database query.
parameterised query
A query where values are bound separately from the SQL text.
inference attack
Deducing hidden data by combining permitted query results.
T-SQL
Microsoft SQL Server's dialect of SQL.
differential privacy
A formal method of adding noise so individuals cannot be identified.
