Database security: through the front door and the side door

Databases leak in two very different ways: queries built carelessly from user input, and aggregate statistics that reveal more than anyone intended. I explored both against a SQL Server lab database, and both changed how I think about building data and AI products.

The 30-second version

  • Did: two kinds of attack on a Microsoft SQL Server database inside a lab VM: SQL injection through an application's inputs, and inference attacks that recover private records from statistics that were supposed to be safe.
  • With: T-SQL, the application's front end and the database's own structure.
  • Learned: databases leak through the front door (queries built from untrusted input) and the side door (aggregates that reveal individuals), and the fixes for each are completely different.
Front door

SQL injection: when input becomes instructions

SQL injection happens when an application builds a query by pasting user input into SQL text. The database cannot tell which parts the developer wrote and which parts the user typed, so input that contains SQL syntax changes the meaning of the query: a login check stops checking, a search returns other tables, an update touches every row.

Built by gluing strings
query = "SELECT * FROM users WHERE name = '"
        + user_input
        + "'"

The user's text becomes part of the SQL itself. Whoever controls the input can rewrite the logic.

Parameterised
query = "SELECT * FROM users WHERE name = @name"
cmd.Parameters.Add("@name", user_input)

The SQL is fixed first; the input is sent separately and can only ever be treated as a value.

Find where input meets a query

Identify fields whose values clearly end up in database queries, and how the app behaves on unusual input.

Infer the hidden query

Reason about what SQL the application must be running, from its behaviour and any errors it exposes.

Enumerate carefully

Use what the database reveals about its own structure to understand what data is reachable, all inside the lab.

Document precisely

Record each finding in the structured format required, as a real assessment report would.

Side door

Inference: learning secrets from "safe" statistics

The second half of the project needed no bug at all. Suppose a database hides individual rows and only answers aggregate questions such as counts, sums and averages, over groups. Each answer looks harmless. But two overlapping questions can differ by exactly one person, and subtracting them reveals that person's value. This is called a differencing attack, and it is why releasing statistics is a genuine privacy problem.

Defences here are statistical rather than syntactic: refuse aggregates over very small groups, track and block overlapping query sets, or add carefully calibrated random noise so no single person's presence changes an answer meaningfully. That last idea is differential privacy, now used by census bureaus and large tech companies.

Looking back

What it taught me

  1. Never build SQL with strings. Parameterisation is a one-line habit that removes a whole category of breach.
  2. Aggregates are not anonymous. Overlapping statistics can rebuild individual records; this matters for any analytics or AI product built on personal data.
  3. Security and privacy are one topic. This project connected directly back to my data-science work.
Reference

Key terms

SQL injection
User input altering the structure of a database query.
parameterised query
A query whose values are bound separately from its SQL text.
T-SQL
Microsoft SQL Server's dialect of SQL.
inference attack
Deducing hidden data by combining permitted results.
differencing attack
Subtracting two overlapping aggregates to isolate one record.
differential privacy
A formal guarantee, achieved with noise, that individuals cannot be singled out.
