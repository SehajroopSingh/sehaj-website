Network forensics: investigating a man-in-the-middle attack

Given recordings of real network traffic, I played the analyst: reconstruct what an attacker sitting between two machines saw, changed and stole, then automate the analysis so it could be run again on the next incident.

The 30-second version

  • Did: a network-forensics investigation: given packet captures of intercepted traffic, work out what the attacker did, which systems and accounts were affected, and what was taken.
  • With: Wireshark for manual inspection, and a small Python program using pyShark to automate the repetitive parts of the analysis.
  • Learned: to read protocols at the byte level, to use RFCs as the source of truth for what "normal" looks like, and how much an attacker can see on an unencrypted network.
Background

When someone sits in the middle

A man-in-the-middle attack puts the attacker between two parties who think they are talking directly. On a local network the classic route is ARP spoofing: the attacker keeps telling machines "the router is me", so traffic flows through them first. Anything not encrypted, from web logins to chat messages, can then be read or altered.

The investigation

Reading the packets

Get the lay of the land

Which hosts are talking, over which protocols, and when. Conversation and protocol statistics narrow millions of packets to the few streams that matter.

Spot the anomalies

Duplicate or flapping ARP replies, traffic routed through an unexpected machine, and sessions that look unlike their RFC. HTTP and IRC both have precise specs, so deviations stand out.

Follow the streams

Reassemble whole conversations to see what was said, sent or downloaded, and which credentials crossed the wire in a recoverable form.

Automate it

Re-do the key filters as a pyShark script so the analysis is repeatable on the next capture instead of a one-off set of clicks.

Why RFCs matter

When you are not sure whether something is suspicious, the protocol standard is the referee. Knowing exactly what a well-formed HTTP request or IRC command looks like is what lets an analyst say "this is wrong" with confidence.

Defence

How to defend against it

Encrypt everything
TLS (HTTPS) means an interceptor sees only ciphertext; HSTS stops downgrades to plain HTTP.
Protect the LAN
Dynamic ARP inspection, port security and segmented networks make spoofing much harder.
Strong credentials
Weak passwords captured as hashes can be cracked offline; length and MFA blunt that.
Monitor
Network monitoring that flags ARP anomalies and unusual flows catches this in hours, not months.
Looking back

What it taught me

  1. Plaintext is public. Seeing a real login travel across a capture made "use HTTPS" visceral.
  2. Tools first, then code. Wireshark to understand, a script to repeat. That split is how I still approach any new data problem.
  3. Specs beat intuition. The RFC answered questions my guesses kept getting wrong.
Reference

Key terms

PCAP
A packet capture file: a recording of network traffic.
ARP spoofing
Sending forged address-resolution replies so traffic is routed through the attacker.
Wireshark / pyShark
The standard packet analyser, and a Python wrapper for scripting it.
RFC
The published standard that defines how an internet protocol must behave.
stream reassembly
Rebuilding a full conversation from many individual packets.
