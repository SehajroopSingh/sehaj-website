Building a processor in C, one clock cycle at a time

A simulator for a five-stage, multi-cycle MIPS processor. It reads a program of 32-bit machine words, then plays the hardware: a control state machine sets the datapath's signals every cycle, registers latch on the clock edge, and each instruction walks through fetch, decode, execute, memory and write-back until the program ends.

The 30-second version

  • What: a functional model of a MIPS CPU written in C. It runs real MIPS machine code and reports the exact state of the processor after every clock cycle.
  • Instructions: add, slt, addi, lw, sw, beq and j, plus a special end-of-program word.
  • The heart of it: a 13-state finite state machine. Each state sets the control signals for one cycle and picks the next state from the instruction's type.
  • Graded by machine: a GitHub Actions autograder compared every control signal, every internal register and every programmer-visible register, cycle by cycle, against the reference.
Background

Single-cycle vs multi-cycle

The simplest processor does all of an instruction's work in one long clock cycle. That works, but the clock has to be slow enough for the slowest instruction (a load, which reads memory twice), so every add pays for the slowest case.

A multi-cycle processor breaks each instruction into short steps and gives each step one fast cycle. Simple instructions finish in three or four cycles, loads take five, and the same hardware (one memory, one ALU) is reused across steps instead of duplicated. The price is control: something has to remember which step we're on and drive the right signals. That something is a finite state machine, and building it is most of this project.

Part 1

The datapath

The datapath is the plumbing: storage elements and the wires between them. Between steps, intermediate values are parked in internal registers the programmer never sees: IR holds the instruction, A and B hold the two source registers, ALUOut holds the ALU's result and MDR holds what came back from memory.

Which wire wins at each junction is decided by multiplexers, and each multiplexer has a select signal: IorD picks whether memory is addressed by the PC or by ALUOut, ALUSrcB picks between B, the constant 4, the immediate and the shifted immediate, and so on. Those signals, plus enables like MemRead and RegWrite, are the control FSM's output.

Part 2

The control state machine

Every instruction starts the same way: Fetch reads the instruction into IR and bumps the PC by 4, and Decode reads both source registers and, speculatively, computes the branch target in case it turns out to be a branch. From there the FSM branches on the instruction type and returns to Fetch when the instruction is done.

Part 3

How I built it

The coursework handed over a skeleton that already ran add, plus the input parser, the memory and the output code. Everything else was mine, in five autograded tasks:

Classify instructions (10 pts)

Map every opcode to its type: R-type, memory, branch, jump, immediate, or end-of-program. All R-type instructions share opcode 0 and are told apart later by their function field.

Decode in the FSM (10 pts)

Teach the Decode state where to go next for each instruction type: memory instructions to address calculation, branches and jumps to their completion states, immediates to their own execute state.

The full FSM (15 + 15 pts)

Write every state: the control signals it asserts and its successor. Then extend the textbook diagram with three states it doesn't have, I-type execute, I-type complete and a terminal exit state that never leaves itself.

Under the hood

Each state starts by clearing every control signal, then sets only the ones it needs. That makes the FSM easy to check against the diagram: the code for a state reads exactly like the bubble in the figure. The addi states reuse the load path's ALU settings (A plus sign-extended immediate) but write the result straight back to rt instead of going to memory.

The datapath (50 pts)

Make each stage honour the signals instead of assuming add: memory reads must use the right address (PC on fetch, ALUOut on a load), the ALU must add, subtract or follow the function field depending on ALUOp, and write-back must pick the right destination and the right source.

Under the hood

The subtle part is the clock. The simulator keeps two copies of the internal registers, current and next. Every stage reads only the current values and writes only the next ones; at the end of the cycle next is copied into current. That mirrors real hardware, where registers only change on the clock edge, and it stops one stage from seeing a value another stage produced in the same cycle.

// one clock cycle (shape of the main loop)
state = FSM(state, &IR_meta);   // set this cycle's control signals
instruction_fetch();            // each stage reads curr_*, writes next_*
decode_and_read_RF();
execute();
memory_access();
write_back();
curr_pipe_regs = next_pipe_regs; // the clock edge

Test my own programs

The public tests were only part of the grade; hidden programs ran too. I wrote memory files that exercise one instruction at a time (a lone lw, a taken and a not-taken beq, a jump backwards) and checked the register dump after every cycle by hand before trusting the combined programs.

Why this matters

Pipelined processors, the ones in every phone and laptop, overlap these same five steps across five instructions at once. Getting each step right in isolation, with registers that only change on the clock edge, is exactly the mental model you need to understand hazards, forwarding and stalls later.

Looking back

What it taught me

  1. Hardware is a timing problem. Most of my bugs were not wrong arithmetic but values read one cycle too early or too late. The current/next register split is the fix, and it only clicks once you have broken it.
  2. Control is data. Once the FSM was a table of states and signals, adding addi was two new rows, not new logic sprinkled through the datapath.
  3. Test one instruction at a time. A combined program that fails tells you nothing. A one-line program that fails tells you the exact state and signal.
  4. Read the spec, not the slides. The coursework's ALUOp encoding deliberately differed from the lecture slides. Matching the autograder meant trusting the handout over memory.
Reference

Key terms

MIPS
A classic RISC instruction set: fixed 32-bit instructions, 32 registers, loads and stores as the only memory access.
multi-cycle
A design where each instruction takes several short clock cycles, reusing one ALU and one memory across steps.
datapath
The registers, ALU, memory and wires that values flow through.
control signal
A wire from the control unit that enables a write or selects a mux input, e.g. MemRead, RegWrite, ALUSrcB.
FSM
Finite state machine. Here: 13 states, each one clock cycle, each with fixed control outputs.
IR / MDR
Instruction register and memory data register: hold the fetched instruction and the loaded word between cycles.
ALUOut
Holds the ALU result for the next cycle: an address, a sum, or a branch target.
CPI
Cycles per instruction. Between 3 and 5 here, depending on the instruction.
