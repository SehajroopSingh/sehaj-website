Web security: making a browser betray its user

Two of the most common web bugs come from the browser doing exactly what it is designed to do. I found and demonstrated cross-site scripting and cross-site request forgery in a deliberately vulnerable app, then mapped each one to the defence that actually closes it.

The 30-second version

  • Did: found and demonstrated two of the most common web vulnerabilities, cross-site scripting (XSS) and cross-site request forgery (CSRF), against an intentionally vulnerable web app.
  • Covered: how browsers decide what code to trust, how sessions and cookies work, and how sanitisers fail when they block the wrong things.
  • Learned: to see a web page the way an attacker does, and which defences actually close each hole.
Background

Two ways to make a browser betray its user

Browsers trust code that comes from a site, and they attach your cookies to any request sent to that site. XSS abuses the first: if a site echoes user input back into a page without encoding it, an attacker's script runs as if the site wrote it, with access to the page and the user's session. CSRF abuses the second: a page on another site quietly triggers a request to the real one, and the browser helpfully sends the victim's cookies along.

The work

Finding the holes

Map the inputs

Every field, URL parameter and stored value that ends up rendered on a page is a candidate. Stored inputs are the most dangerous because they hit every visitor.

Test the filters

Basic sanitisers often block a few obvious patterns and miss equivalent ones. Understanding where the input lands, inside HTML, an attribute or a script, decides what gets through.

Demonstrate impact

Show what a real attacker would gain, such as reading data from the page or performing an action as the user, in a contained lab.

Forge a request

For CSRF, build an outside page that triggers a state-changing action on the app, proving the app could not tell a forged request from a real one.

Defence

How to defend against it

Encode output, by context
Escape data for exactly where it is placed (HTML, attribute, JavaScript); modern frameworks do this by default.
Content Security Policy
Tells the browser which scripts may run, which neuters most injected scripts.
HttpOnly + SameSite cookies
Scripts cannot read the session cookie, and cross-site requests do not carry it.
CSRF tokens
A secret per-session value that a forged request cannot know.
Looking back

What it taught me

  1. Blocklists lose. Filtering "bad" strings fails; encoding output by context succeeds.
  2. The browser is part of the system. Security decisions happen client-side too, and you have to design for them.
  3. Defaults matter. Most of these bugs disappear with a modern framework's safe defaults left switched on.
Reference

Key terms

XSS
Cross-site scripting: attacker-controlled script running in a trusted site's page.
stored vs reflected XSS
Saved and shown to every visitor / bounced back from a single request.
CSRF
Cross-site request forgery: tricking a logged-in browser into sending a request.
CSP
Content Security Policy: a browser rule set limiting which scripts can run.
SameSite
A cookie flag that keeps cookies off cross-site requests.
