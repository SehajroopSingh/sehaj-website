Web security: making a browser betray its user

Two of the most common web vulnerabilities come from the browser doing exactly what it was designed to do. I found and demonstrated cross-site scripting and cross-site request forgery in a deliberately vulnerable app, then mapped each one to the defence that actually closes it.

The 30-second version

  • Did: found and demonstrated cross-site scripting (XSS) and cross-site request forgery (CSRF) in a deliberately vulnerable web application, then mapped each to the defence that actually closes it.
  • Core idea: browsers make two trust decisions automatically: they run any script that appears to come from a site, and they attach your cookies to any request sent to that site. XSS abuses the first, CSRF the second.
  • Learned: why blocklist filters fail, why the fix depends on where data lands in a page, and how much of web security is good framework defaults.
Attack 1

Cross-site scripting: getting the site to run your code

If a site takes user input (a comment, a profile field, a search term) and puts it back into a page without encoding it, the browser cannot tell the difference between the site's own code and code the attacker typed. That script then runs with the site's full privileges: it can read the page, act as the logged-in user and send data elsewhere. Stored XSS is saved and served to every visitor; reflected XSS bounces back from a single crafted link.

A big part of the work was understanding context. A filter that strips one obvious tag may still let through input that lands inside an HTML attribute, a JavaScript string or a URL, where entirely different characters matter.

Where input landsCorrect defence
Between HTML tagsHTML-encode < > & and quotes
Inside an HTML attributeAttribute-encode, and always quote the attribute
Inside JavaScriptJavaScript-encode, or better, pass data via JSON, never by string-building
In a URLURL-encode, and allow only safe schemes (no javascript:)

Output encoding depends on context. This is why "just filter bad words" never works.

Attack 2

Cross-site request forgery: making the browser act for you

CSRF needs no bug in how the site displays data. The victim is logged in to the real site; while that session is active they visit a page the attacker controls. That page silently submits a request to the real site (change an email, move money, alter settings), and the browser helpfully attaches the victim's session cookie. From the server's point of view it is a perfectly valid, authenticated request.

The work

How I approached it

Map every input

List every field, URL parameter and stored value that ends up rendered somewhere, and every action that changes state.

Probe the filters

Work out what the sanitiser blocks and, more importantly, the context each input lands in, which decides what it misses.

Demonstrate impact safely

Show what an attacker would actually gain inside the lab app, rather than just making a pop-up appear.

Test state-changing actions for CSRF

Check whether important actions can be triggered from another origin without any secret the attacker cannot know.

Looking back

What it taught me

  1. Blocklists lose. Filtering "bad" input fails; encoding output by context succeeds.
  2. The browser is part of your system. Its automatic trust decisions are where both attacks live.
  3. Defaults are security. Most of these bugs disappear with a modern framework's safe defaults left switched on.
