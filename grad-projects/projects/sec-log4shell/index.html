Log4Shell: one log line, full remote control

In December 2021 a single string written to a log file could take over servers across the internet. I worked through Log4Shell hands-on in an isolated lab: the incident timeline, how three ordinary features chain into remote code execution, and how defenders find and shut it down.

The 30-second version

  • Did: studied and safely reproduced, in an isolated lab, Log4Shell (CVE-2021-44228): the December 2021 flaw in Apache Log4j that let attackers run code on a server just by getting a string written to its logs.
  • Covered: Log4j's lookup substitution, Java's JNDI directory API, LDAP, and how they chain into remote code execution; then detection and mitigation.
  • Why it is famous: rated CVSS 10.0, the maximum, and present deep inside a vast number of Java products, many of whose owners did not know they used Log4j at all.
The incident

December 2021, day by day

  1. Nov 24, 2021Alibaba Cloud's security team privately reports the flaw to the Apache Software Foundation.
  2. Dec 9–10Exploit details become public; CVE-2021-44228 is published and Log4j 2.15.0 is released. Mass scanning begins within hours.
  3. Dec 13–142.15.0 proves incomplete (CVE-2021-45046); 2.16.0 removes message lookups entirely and disables JNDI by default.
  4. Dec 17–18A denial-of-service issue (CVE-2021-45105) is fixed in 2.17.0.
  5. Dec 282.17.1 closes a further, harder-to-exploit configuration issue (CVE-2021-44832).

Four security releases in under three weeks: a reminder that the first patch for a critical bug is often not the last.

How it works

One log line, full remote control

Log4j supported lookups: placeholders written as ${prefix:name} inside a log message that are replaced with a value at runtime, handy for adding things like environment details to logs. One prefix used JNDI, Java's API for looking up objects in naming and directory services, including remote ones over LDAP. Log4j performed lookups on the whole message, including parts that came from users.

Why it spread so fast

The vulnerable code lived several layers down in other libraries and products. Many organisations could not answer the simple question "do we use Log4j?", so exposure lasted for weeks. That experience is a big reason software bills of materials (SBOMs) became standard practice.

The work

Reproducing it safely

Learn the building blocks

Java class loading, Log4j's lookup syntax, JNDI and LDAP, and how they normally interact.

Stand up the lab

Run the vulnerable service and the supporting LDAP and HTTP servers entirely inside the isolated VM, with nothing reachable from outside.

Trace the chain

Follow a logged string through the lookup, the outbound connection and the class load, confirming each hop in logs and network traffic.

Look at it as a defender

Identify the traces left behind (lookup strings in logs, unexpected outbound LDAP connections from an app server) and what breaks the chain at each step.

Defence

Breaking the chain at every link

LayerDefenceBreaks which step
LibraryUpgrade Log4j (2.17.1+ for Java 8)The lookup never happens
InventoryDependency scanning and SBOMsLets you find every affected system in minutes
NetworkEgress filtering: app servers should not open arbitrary outbound connectionsThe LDAP query and class download fail
RuntimeModern Java defaults restrict remote class loadingThe remote class is not executed
DetectionAlert on lookup strings in logs and on unusual outbound trafficSpots attempts and compromises
PerimeterWAF rules (temporary)Buys time; easily bypassed by obfuscation, so not a fix
Looking back

What it taught me

  1. Your dependencies are your attack surface. None of the hardest-hit companies wrote the vulnerable code.
  2. Features compose into exploits. No single step was a bug on its own.
  3. Egress control is underrated. Blocking unexpected outbound traffic would have stopped most real-world exploitation.
  4. Real incidents teach best. Working through a famous CVE made patching and inventory feel urgent, not bureaucratic.
Reference

Key terms

CVE
Common Vulnerabilities and Exposures: a public ID for a known flaw.
CVSS
A 0–10 severity score; Log4Shell scored 10.0.
Log4j
A very widely used Java logging library.
lookup
A ${prefix:name} placeholder Log4j replaces at runtime.
JNDI
Java Naming and Directory Interface: looks up objects, including remote ones.
LDAP
A directory protocol that can serve such objects.
RCE
Remote code execution.
SBOM
Software bill of materials: an inventory of every dependency in a product.
