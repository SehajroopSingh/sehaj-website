Log4Shell: one log line, full remote control

In late 2021 a single string written to a log file could take over servers across the internet. I worked through Log4Shell hands-on in an isolated lab: how three ordinary features chain into remote code execution, and how defenders find and shut it down.

The 30-second version

  • Did: studied and reproduced, in an isolated lab, Log4Shell (CVE-2021-44228), the 2021 Apache Log4j vulnerability that let attackers run code on servers simply by getting a string written to a log.
  • Covered: how Log4j's lookup feature, Java's JNDI and an LDAP server chain together into remote code execution, and how defenders detect and mitigate it.
  • Learned: how a convenience feature deep in a dependency became one of the most serious vulnerabilities in years.
Background

One log line, full remote control

Log4j is a logging library used in a huge share of Java software. It supported "lookups": placeholders inside a logged message that get replaced with a value at runtime. One kind of lookup used JNDI, Java's directory service API, which can fetch objects from a remote server. So if an attacker could get a specially crafted string logged, for example in a username or an HTTP header, the server would reach out to the attacker's directory server and end up loading and running code from it.

The work

Understanding it hands-on

Learn the pieces

Java, Log4j's lookup substitution, JNDI and LDAP, and how they normally fit together.

Trace the chain

Follow a request from the logged string to the outbound lookup and the class being loaded.

Reproduce safely

Recreate the behaviour against a deliberately vulnerable service in a closed lab environment.

Detect and mitigate

Look at the traces it leaves (unexpected outbound connections, tell-tale strings in logs) and at what stops it.

Why it was so bad

Log4j was buried several layers deep in countless products, so many organisations did not even know they used it. Inventorying dependencies became an emergency overnight, which is why software bills of materials (SBOMs) suddenly mattered.

Defence

How to defend against it

Patch
Upgrade Log4j; fixed versions disable the dangerous lookups.
Know your dependencies
Dependency scanning and SBOMs answer "are we affected?" in minutes.
Egress filtering
Servers rarely need to open arbitrary outbound connections; blocking that breaks the chain.
Treat input as data
Never let logged user input be interpreted; WAF rules buy time but are not a fix.
Looking back

What it taught me

  1. Your dependencies are your attack surface. The vulnerable code was not written by any of the companies that got hit.
  2. Features compose into exploits. No single step was a bug on its own.
  3. Real CVEs teach best. Working through a famous incident made patching and inventory feel urgent, not bureaucratic.
Reference

Key terms

CVE
A public identifier for a known vulnerability.
Log4j
A widely used Java logging library.
JNDI
Java Naming and Directory Interface: an API for looking up (including remote) objects.
LDAP
A directory protocol that can serve those objects.
RCE
Remote code execution: running attacker code on someone else's machine.
SBOM
Software bill of materials: an inventory of a product's dependencies.
