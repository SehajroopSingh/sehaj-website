API security: authentication is the easy half

Most modern breaches are not clever exploits; they are an API that forgot to ask "is this caller allowed to see this?". I audited a REST API for exactly those mistakes, from broken object-level authorisation to carelessly verified tokens.

The 30-second version

  • Did: audited a REST API for the mistakes that cause most modern breaches: missing authorisation checks, trusting client-supplied identifiers, unsafe file paths and weak tokens.
  • With: HTTP request tooling, the API's own documentation, and an understanding of how JSON Web Tokens (JWTs) are built and verified.
  • Learned: that authentication ("who are you?") is the easy half; authorisation ("are you allowed to do this?") is where APIs fail.
Background

APIs trust too much

Almost every app is now a front end over an API. Each request carries everything the server needs: a path, parameters, headers and usually a token that says who the caller is. The server has to check, on every single request, not just that the token is valid but that this caller may touch this object. Skip that second check once and anyone can read anyone else's data by changing an ID in the URL.

The work

What I tested

Read the contract

Use the API's documentation and its responses to map endpoints, parameters and what each one should allow.

Anatomy of a request

Understand exactly how headers, query parameters, cookies and authorisation tokens are sent and interpreted.

Probe authorisation

Check whether objects belonging to other users, or admin-only actions, are reachable by changing identifiers or roles.

Inspect the tokens

Decode JWTs to see their claims and how they are signed, and reason about what happens if the server verifies them carelessly.

Defence

How to defend against it

Authorise every object
Check ownership or role server-side on every request, never relying on what the client sends.
Validate paths and input
Normalise and whitelist file paths and parameters.
Verify tokens strictly
Fix the allowed algorithm, use strong secrets or keys, and keep token lifetimes short.
Least data returned
Return only the fields the caller needs, not whole internal objects.
Looking back

What it taught me

  1. Authorisation is per request. Logging in once means nothing if each endpoint does not re-check permissions.
  2. Tokens are only as good as their verification. A JWT is just signed JSON; the security is in how strictly the server checks it.
  3. Directly useful in my work. Integrating AI systems with client APIs, these are the first questions I now ask.
Reference

Key terms

REST API
A web interface where resources are addressed by URL and manipulated with HTTP methods.
IDOR / BOLA
Insecure direct object reference: accessing another user's object by changing its ID.
JWT
JSON Web Token: a signed, base64-encoded set of claims used for authentication.
path traversal
Using ../ style paths to reach files outside the intended folder.
