API security: authentication is the easy half

Most modern breaches are not clever exploits; they are an API that forgot to ask "is this caller allowed to see this?". I audited a REST API for exactly those mistakes, from broken object-level authorisation to carelessly verified tokens.

The 30-second version

  • Did: audited a REST API for the mistakes behind most modern data breaches: missing authorisation checks, trusting identifiers sent by the client, unsafe file paths and loosely verified tokens.
  • With: HTTP request tools, the API's own documentation, and a working understanding of how JSON Web Tokens (JWTs) are built, signed and verified.
  • Learned: authentication answers "who are you?" once; authorisation must answer "are you allowed to do this, to this object?" on every single request.
Background

Anatomy of an API request

Every call to an API is self-contained: the server knows only what this one request tells it. Understanding exactly which parts the client controls (all of them) is the starting point for any audit.

GET/api/v1/orders/1042HTTP/1.1
Hostshop.example.com
AuthorizationBearer eyJhbGciOi… who the caller claims to be
Cookiesession=… sometimes used instead of a token
Query?include=items&format=json options the server reads

The highlighted ID and token are both supplied by the client. The server must verify the token and check that order 1042 belongs to whoever it identifies.

Problem 1

Broken object-level authorisation

The most common API flaw (number one on the OWASP API Security Top 10) is simple: the server checks that the token is valid, then returns whatever object ID was requested. Change 1042 to 1043 and you see someone else's order. Nothing was "hacked"; one check was missing.

RequestAlice's ordersBob's ordersAdmin endpoint
Alice's token, expected✔ allowed✘ must be denied✘ must be denied
What a broken API does✔ allowed✔ returned anyway✔ returned anyway

An authorisation matrix. Auditing an API is largely filling in this table for every endpoint and checking the server enforces it.

I worked through the documented and undocumented endpoints testing exactly this: objects belonging to other users, admin-only actions, and file-retrieval endpoints that build file paths from client input (where ../ sequences can escape the intended folder, a path traversal).

Problem 2

Tokens are only as good as their verification

A JWT is three base64-encoded parts joined by dots: a header naming the signing algorithm, a payload of claims (user ID, role, expiry) and a signature. Anyone can decode and read the first two; the signature is what stops them being edited. Security therefore depends entirely on how strictly the server verifies it.

The classic failures all come from careless verification: accepting tokens that declare no algorithm, signing with a short guessable secret, not checking expiry, or trusting a role claim without confirming it server-side.

Defence

How to build an API that does not leak

RiskDefence
Broken object-level authorisationCheck ownership or permission server-side on every request; deny by default
Broken function-level authorisationSeparate admin routes and enforce roles in one central place
Path traversalNever build file paths from input; use IDs mapped to files, and normalise + whitelist
Weak JWT handlingPin the expected algorithm, use strong keys, verify expiry, keep lifetimes short
Excessive data exposureReturn only the fields the caller needs, not whole internal objects
Unknown endpointsKeep an inventory; retire old versions; document everything that is live
Looking back

What it taught me

  1. Authorisation is per request. Logging in once means nothing if each endpoint does not re-check permissions.
  2. Readable is not secure. JWT payloads are plain JSON; only verification makes them trustworthy.
  3. Directly relevant to my work. When I connect AI systems to a client's APIs, these are now the first questions I ask.
